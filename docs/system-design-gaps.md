# System Design Gap Analysis

This document tracks the gap between the target architecture in [system-design.md](system-design.md) and the current OpenSlot MVP implementation. Some gaps are intentional MVP scope cuts; others are implementation risks to close before treating the system design as production reality.

## Summary

The current app has a strong one-on-one scheduling core: Supabase-backed auth/profile/event types, public booking pages, slot computation, five-minute holds, database overlap constraints, idempotent confirmation/cancellation/rescheduling when keys are supplied, booking events, outbox processing, one configurable pre-meeting reminder, calendar OAuth/sync/write support, and signed tenant webhook deliveries.

The target system design is broader. It assumes organization-scoped tenancy, Edge Functions for risky public/provider boundaries, group and team scheduling, paid bookings, provider watch callbacks, stronger transaction boundaries, Supabase-native queues/cron, realtime dashboard freshness, and enterprise hardening.

## Gap Matrix

| Area | Target in `system-design.md` | Current implementation | Gap / impact | Likely next work |
| --- | --- | --- | --- | --- |
| Tenant boundary | `org_id`-scoped tenancy with `organizations`, `organization_members`, org roles, org RLS, and tenant-owned webhook/domain records. | Data is primarily profile/host scoped. `event_types`, availability, holds, bookings, calendar connections, and webhook endpoints point at `profiles`/`user_id`/`host_user_id`. | No real organization/team account boundary, membership roles, org-level permissions, or org-level billing/domain ownership. | Add org/membership tables, backfill one org per profile, move ownership columns toward `org_id` plus host/member relations, and rewrite RLS/API scoping. |
| API/runtime boundary | Public booking writes, provider callbacks, payment webhooks, and integration workers run as Supabase Edge Functions with isolated secrets and function config. | Current public and worker surfaces are Next.js route handlers under `src/app/api/*`, deployed with the web app. | Pragmatic for MVP code reuse, but high-risk public/provider endpoints are coupled to the web app runtime and deployment lifecycle. | Keep authenticated dashboard APIs in Next routes. Move or mirror public booking writes, Stripe webhooks, and calendar provider webhooks into Edge Functions when isolation becomes worth the operational split. |
| Scheduling ownership model | Event types belong to orgs and can have multiple hosts through `event_type_hosts`; schedules are named containers with validity windows. | Event types belong to one profile through `event_types.user_id`; named `schedules` belong to the host profile; availability rules/overrides and event types are schedule-scoped. | No team event host roster, host weighting, required hosts, or future schedule validity windows. | Add `event_type_hosts`, migrate one-host event types into a single required host row, and extend schedules with validity windows when needed. |
| Group capacity | Group events use `group_slot_inventory` with locked seat counts and `party_size` on holds. | Holds and bookings reserve one host time range only; no group slot inventory, seat counts, or party size. | Cannot support "up to N attendees" events safely; exclusion constraints only express one active reservation per host/time. | Add `group_slot_inventory`, capacity fields on event types, `party_size` on holds/bookings, and inventory reservation/promote/release paths. |
| Round-robin and collective scheduling | Host assignment uses transaction-scoped candidate selection plus reservation constraints; collective bookings can allocate multiple hosts. | Slot lookup and hold creation take a specific `hostUserId`; bookings store a single `host_user_id`. | No deterministic team assignment, load balancing, required-host collective meetings, or multi-host booking records. | Add assignment engine, `booking_hosts`, host availability intersection logic, and tests for concurrent team assignment. |
| Booking attendees/answers | Bookings support attendees, structured answers, guest tokens, and host allocation rows. | Bookings store one guest name/email/timezone, freeform notes, cancellation/reschedule tokens, and structured answer snapshots for event-type invitee questions. | No multiple attendees, and provider event refs are stored separately from the proposed `booking_hosts` model. | Add `booking_attendees` and decide whether calendar refs remain separate or move behind host allocation rows. |
| Paid bookings | Stripe Checkout/Connect, `payment_sessions`, event type pricing fields, payment webhooks, and payment reconciliation. | No Stripe dependency, no payment API routes, no payment tables, and no payment fields on event types/bookings. | Paid booking flows are not implemented; holds always confirm directly as free bookings. | Add payment configuration to event types, create checkout/session APIs, Stripe webhook handling, payment session reconciliation, and tests for delayed webhook completion. |
| Booking transaction boundaries | Booking confirmation, cancellation, and rescheduling are short authoritative database transactions, with side effects queued after the booking state commits. | Hold creation and rescheduling use RPCs. Confirmation and cancellation are multi-step service-role calls from application code: insert/update booking, update hold/reservation, append events, then enqueue outbox rows. | Database constraints still protect one-on-one overlaps, but partial state is possible if a later step fails after an earlier write succeeds. | Move confirmation and cancellation state transitions into database RPCs or another true transaction boundary; enqueue deterministic outbox rows as part of the same transaction where feasible. |
| Hold idempotency | Every mutating public endpoint, including hold creation, requires idempotency. | Booking confirm/cancel/reschedule accept optional idempotency keys. Hold creation has no idempotency key in its validation schema. | Browser retries can create multiple sequential hold attempts, though reservation constraints prevent the same slot from being double-held. | Add hold idempotency support and cache conflict/success responses consistently with booking mutations. |
| Public abuse controls | Public booking endpoints use strict validation, rate limiting, CAPTCHA/bot protection, and signed tokens. | Zod validation and high-entropy hold/cancel/reschedule tokens exist. No app-level rate limiter or CAPTCHA is implemented for slot/hold/booking routes. | Public endpoints are more exposed to scraping, brute-force attempts, and high-volume hold spam than the target design allows. | Add IP/user-agent aware rate limits, optional CAPTCHA/Turnstile for public booking mutations, and monitoring for conflict/hold spikes. |
| Background job platform | Supabase Cron/`pg_cron` plus `pgmq` queues for expiry, provider sync, watch renewal, reminders, payment reconciliation, cleanup, and webhook/provider backoff. | Vercel Cron calls Next route handlers for outbox processing, webhook delivery processing, and calendar sync. Outbox/delivery ledgers are normal tables with leasing RPCs, not `pgmq`. | Works for MVP, but background work is tied to Vercel and lacks several target jobs. | Decide whether to stay Vercel-based or move to Supabase Cron/Queues; document one worker platform as canonical before adding more jobs. |
| Hold expiry sweeps | Active holds expire automatically and release reservations on a schedule. | Expired holds/reservations are cleaned lazily during hold creation or confirmation/reschedule paths. | Expired rows may remain active until touched by another operation, increasing reliance on lazy cleanup paths. | Add a scheduled expiry worker that marks expired holds and host reservations idempotently. |
| Reminders | Reminder jobs enqueue 24h/1h/10m or product-defined reminder notifications. | Event types can schedule one pre-meeting email reminder through `outbox_events.available_at`, with guest/host email recipient toggles and cancellation/reschedule suppression at processing time. | MVP reminders do not yet support multi-step workflows, post-meeting follow-ups, no-show style automation, templates per event type, or scheduler SLAs below the active worker cadence. | Add multi-step workflow rules, follow-up/no-show automation, per-event template customization, and production scheduler monitoring for queue latency. |
| Calendar watch callbacks | Google `events.watch`, Microsoft Graph subscriptions, callback endpoints, renewal jobs, and sync-token repair paths keep busy cache fresh. | OAuth, calendar list sync, busy-cache refresh, provider availability filtering, provider event writes, provider watch/subscription creation, renewal, and webhook callbacks are implemented in Next route handlers. | Incremental sync-token repair is still narrower than the target architecture, and worker cadence still depends on the selected scheduler. | Add provider-specific sync-token repair/backoff metrics and decide whether these provider callbacks should move to Edge Functions later. |
| Final provider availability verification | Booking commit can perform a final live provider check when cache freshness is poor or watch health is degraded. | Confirmation can run an optional live provider busy-window check with `CALENDAR_FINAL_AVAILABILITY_CHECK=stale` when cache/watch health is stale. | The check is opt-in and only covers connected provider calendars; disabled environments still trust holds plus database overlap constraints. | Decide the production default and add monitoring for stale-cache verification failures. |
| Webhook endpoint model | Tenant webhooks are org-scoped and secret handling is explicitly designed for signing, rotation, and endpoint lifecycle. | Webhook endpoints are profile-scoped and store a server-only `secret_token`; create returns the secret once, and list APIs hide it. | Signed delivery works, but org ownership, secret rotation, delivery replay UX, and endpoint lifecycle are narrower than the target tenant model. | Move endpoints to org scope after org tenancy exists; add secret rotation/versioning and replay/diagnostic controls. |
| Realtime dashboard UX | Supabase Realtime keeps host/admin dashboards fresh. | No realtime sync in the UI. | Hosts must refresh/navigate to see new bookings, webhook status changes, or provider sync changes. | Add focused subscriptions or polling for bookings/outbox-derived dashboard state after data contracts stabilize. |
| Storage/assets | Supabase Storage can hold avatars, logos, ICS files, and attachments with access rules. | Profiles have `avatar_url`; there is no committed Storage bucket/policy setup or upload workflow. | Branding/assets are URL-only or external; no controlled upload lifecycle. | Add Storage buckets, policies, upload UI/API, and generated asset cleanup rules when product needs it. |
| Custom domains | Domain mapping uses `domains` rows, DNS verification, TLS status, and frontend routing. | No `domains` table or custom-domain routing. | Public booking pages are username-path based only. | Add domain verification model and frontend host routing once org/branding work exists. |
| Enterprise auth | Supabase SAML/custom OIDC flows support enterprise SSO, with tenant/admin configuration. | App uses Supabase email/password auth surfaces; no enterprise SSO configuration UI or org-level IdP model. | Not enterprise-ready for B2B SSO requirements. | Add org-scoped SSO configuration and test login/domain routing flows when enterprise customers require it. |
| Data residency and sharding | Region/project strategy is explicit for residency-sensitive tenants. | No app-level region/project sharding or tenant residency model. | The design recommendation is not actionable for customer-specific residency yet. | Document deployment-region policy and shard strategy before selling strict residency. |
| Observability | Structured logs, correlation IDs, Metrics API/log drains, Sentry/Datadog/Grafana, and alerts on booking conflicts, queue lag, provider failures, and dead letters. | Worker routes and services log errors, but there is no committed observability stack, correlation-id convention, or alerting plan. | Harder to diagnose production booking/provider/webhook failures. | Add request IDs, structured operational logs, error reporting, dashboard metrics, and alert thresholds. |
| CI and integration testing | CI runs RLS, migration, concurrency, provider contract, and local Supabase integration tests. | GitHub Actions runs the app release gate, npm audit, and local Supabase migration reset/lint. Tests are still mostly Vitest/unit/property tests with mocked Supabase clients. | Schema application is continuously checked, but RLS behavior, real database concurrency, and provider contracts are not continuously verified against the local Supabase stack. | Add local Supabase integration tests, RLS regression tests, and explicit concurrent hold/confirm scenarios. |
| Production deployment model | Deployment target, worker schedules, migrations, env vars, and rollback/DR runbooks are part of the architecture. | Vercel cron config exists and `docs/release.md` covers environment separation, release steps, migration validation, rollback, cron ownership, and backup assumptions. | Deployment is documented, but migrations are still applied out of band and there is no infrastructure-as-code, automated restore drill, or committed observability stack. | Pick final platform ownership, automate deployment/migration steps where appropriate, and add restore/monitoring runbooks tied to the chosen provider. |

## Useful Prioritization

High priority before production hardening:

- Make booking confirmation and cancellation atomic across booking state, reservation state, audit events, and outbox enqueueing.
- Add hold idempotency plus rate limiting/bot protection for public booking mutations.
- Add scheduled hold expiry.
- Expand CI from migration validation into RLS and real database concurrency coverage.
- Decide whether Next route handlers remain the canonical public backend or whether selected public/provider endpoints move to Supabase Edge Functions.

Medium priority for a stronger scheduling product:

- Implement provider watch callbacks and renewal.
- Add final live provider availability checks when cache health is stale.
- Expand reminders into multi-step follow-up workflows.
- Improve observability around queue lag, provider failures, webhook delivery, and booking conflicts.

Major product expansion:

- Add organization tenancy, teams, round-robin/collective scheduling, group capacity, payments, custom domains, enterprise SSO, and data residency/sharding.

## What Is Already Aligned

- Public app tables are not directly exposed to `anon`; public reads and guest writes go through server-side code.
- One-on-one booking conflicts are protected by database exclusion constraints.
- Active holds and confirmed bookings are mirrored into `host_reservations`.
- Booking confirmation, cancellation, and rescheduling support idempotent retries when clients send a key.
- Booking lifecycle events are appended to `booking_events`.
- Side effects are represented as deduped `outbox_events`.
- Pre-meeting reminders use deduped, scheduled `outbox_events` and recheck booking status before sending.
- Calendar provider tokens live in server-only tables and are encrypted before storage.
- Calendar event writes and cancellation retries store external references in `calendar_event_refs`.
- Tenant webhook deliveries are signed and retried through worker processing.
